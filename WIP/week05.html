01 What state is

State is data that changes while the page is open. Which component type is currently selected. What has been placed so far. Whether a request is still loading. All of it is state.

The idea that makes React work is worth stating plainly, because it is the opposite of how you would do it by hand:

The whole model, in one sentence

You change the data, and React redraws whatever needs redrawing. You never touch the page.

There is no code anywhere in this week that adds a list item to the screen. You add an object to an array, and the list on screen follows, because your component describes what the list should look like for whatever the array currently holds. React runs that description again whenever the array changes.

02 useState

useState hands you two things: the current value, and a function for replacing it.

The names are yours to choose; setSomething is the near-universal convention. Call the setter and React re-runs your component with the new value:

Two rules, and both of them bite:

Never assign to the value directly

Assigning changes a variable that is about to be thrown away. Only the setter tells React that something is different.

The setter replaces — it does not merge

For an array, that means handing over a whole new array. This is exactly the pattern from Week 2, and now you can see why it mattered:

The bug that wastes an hour

placements.push(newOne) followed by setPlacements(placements) does nothing visible. The array now holds the new item, but it is the same array object React already had, so React concludes nothing changed and does not redraw. Your data is right and your screen is stale. If adding an item appears to do nothing, this is almost always why.

05 Why keys matter

Every element produced by map needs a key, and React will warn you in the console if you forget. It is not a formality.

When your array changes, React compares the new list against the old one to work out the smallest possible edit. Keys are how it matches an old item to its new self. Without them it guesses by position, and positions shift whenever something is inserted or removed.

The consequence is invisible in a list of plain text and very visible once items hold state of their own — a half-typed input, a marker mid-drag, an open menu. Those things follow the key. If the key is the array index, deleting the first item shifts every other item's identity by one, and their state ends up attached to the wrong row.

A key must be unique among its siblings and must not change between renders. Your id field is exactly that, which is why it is in the object shape.

07 When it breaks

Clicking Add does nothing

Either you mutated the array instead of replacing it — push followed by setPlacements(placements) — or onAdd is not reaching the button. Put a console.log("add") as the first line of addPlacement: if it prints, the click is fine and the problem is the update; if it does not, the prop is not wired up.

The tab freezes as soon as items appear

You wrote onClick={onRemove(p.id)} without the arrow. That calls the function during rendering, which changes state, which triggers another render, forever. Add () => in front.

Warning: Each child in a list should have a unique "key" prop

A map somewhere is producing elements without key. Both maps in Sidebar need one — key={type} on the palette buttons and key={p.id} on the list items.

Two items share the same id

Date.now() returns the same millisecond if two placements are created in the same instant — possible if you ever add several at once. For this course, clicking by hand, it is fine. If you want to be safe, use Date.now() + Math.random().

Cannot read properties of undefined

A prop did not arrive. Check that the name in the parent matches the name in the child exactly — onRemove passed but onDelete expected produces this. Console-log the props object at the top of the child to see what actually came through.

The selected button does not highlight

Either .item.selected is missing from your CSS, or the comparison is failing. The className expression must produce the string "item selected" — log type and selectedType side by side and confirm they are identical strings when they should match.
