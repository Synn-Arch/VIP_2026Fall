01 What happens when you press Run

In Week 5, the Results panel sent two numbers and waited one second for the answer. That works because one second is short. SOLWEIG takes minutes. A browser request that hangs for minutes is fragile, and while it hangs you cannot tell the user anything. So the real site, and yours from this week, splits the wait into small questions:

The first answer is a job id, not a result. After that the browser asks "how far are you?" every two seconds and moves the progress bar. When the answer is done, the map shows the new pictures and the panel the new numbers. This is exactly what the prototype does.

Behind POST /api/jobs the backend does what you did by hand in Week 5: copy the inputs into a fresh folder, raise the canopy in Trees.tif where each tree was placed, run SOLWEIG-light, and turn TMRT_0_0.tif and UTCI_0_0.tif into hourly PNGs, plus a difference picture against the baseline for every hour.

By the end of this week your site should look and behave like the prototype from Week 5: Variable (TMRT or UTCI), Layer (Baseline, Scenario, Difference), opacity, the hour slider, the statistics, the tree list and the Run button. One thing is simpler on purpose: every tree is the same size for now. Choosing tree sizes comes next week.

02 Get the website's model

As promised, SOLWEIG-light got its update: the version that runs the Cool Choices website is faster and checks memory before it starts. It is the same model with the same results, and the same thermal_comfort(...) you called in Week 5, so your Week 5 scripts keep working. Everyone installs it once, into the solweig-light environment from Week 5. It replaces the old version there.

It is published as solweig-light-web.zip (click this link if you want to download it) on our course GitHub, and pip can install it straight from that link:

The last line must print website model ok. --no-deps keeps every other package exactly as it is, which matters for GDAL: pip must not try to rebuild it. If the download fails on your network, download the zip from the link above (do not unzip it) and give pip the file instead: pip install --force-reinstall --no-deps ~/Downloads/solweig-light-web.zip.

The first run is slower

Like in Week 5, the model compiles its numerical kernels the first time it runs after an install, which adds a minute or more. They are cached after that.

04 The backend

The scene folder

The backend runs the model itself now, the baseline included, so it needs the inputs. Make a folder backend/scene/ and copy four files into it from Track A's Week 5 folder: Building_DSM.tif, DEM.tif and Trees.tif from Input_subset_light/, and ownmet_Forcing_data.txt. Only those four, not processed_inputs/ or output_folder/. Commit them: they are small, and everyone's backend needs them.

Week 5's overlays retire

The baseline PNGs now come from the backend, for both TMRT and UTCI, with the same colours as every run. frontend/public/overlays/ from Week 5 is no longer used; you can delete it.

model.py · running SOLWEIG-light (new)

Week 5's run_light.py, cut into small functions that the baseline and every run share. scene_info works out the four corners in longitude/latitude for the map, inside checks a tree is within the scene, plant_trees raises the canopy to TREE_HEIGHT inside CROWN_RADIUS around each tree, and run_solweig is the same call as Week 5. The last two functions let the progress bar follow the model: it writes a file when the sky view step is done, and another after every hour.

render.py · pictures and numbers (new)

For each variable and hour it draws a PNG with a fixed colour range, so baseline and scenario can be compared picture to picture. With a baseline given, it also draws the difference (scenario minus baseline, green where it got cooler) and counts the pixels that changed by more than half a degree. Everything else the panel shows comes from result.json.

baseline.py · the baseline, once (new)

jobs.py · one run at a time (new)

A dictionary of jobs and a single worker thread that takes them off a queue. The thread is what lets POST /api/jobs answer immediately while the model carries on. There is only one, on purpose: the model uses every core it is given, so two runs at once would each take twice as long. The lock is there because the web server reads a job at the same moment the worker updates it.

main.py · the API (replace)

The Week 5 routes stay at the top. Then: the scene, the baseline statistics, starting and checking a run, and the PNGs. The last two routes only hand out names like tmrt_14.png or utci_diff_09.png, so nobody can ask the server for any other file on your computer.

The PNGs are written with Pillow:

Try it

The baseline takes as long as one run (the first time a bit longer, see section 02) and ends with done: .../backend/data/baseline. Then start the server, open localhost:8000/docs, and try POST /api/jobs with {"trees": [{"lng": …, "lat": …}]}, using the center from GET /api/scene. Then GET /api/jobs/{job_id} now and then: phase goes preparing → geometry → simulating (with timesteps_done counting to 24) → rendering → done. A tree far outside the scene, or no tree at all, gets a 400 with the reason.

Saving a backend file stops a run

Jobs live in the server's memory, and --reload restarts the server whenever you save a .py file in backend/. A run that was going is then lost, and the app says "unknown job". Press Run again. While you are only testing runs and not editing the backend, you can start uvicorn without --reload.

05 The frontend

Five files in frontend/src/, all replaced. main.jsx stays as Vite made it, and config.js and components/ResultPanel.jsx from Week 5 are no longer used: delete them.

api.js · the backend's routes (replace)

One function per route, and overlayUrl, which builds the name of the PNG for a variable, hour and layer. Baseline pictures come from /api/baseline/, a run's from /api/jobs/<id>/.

App.jsx · all the state, and the run (replace)

As in Week 5, App owns every piece of state, because the map and the panel both need it. The new part is run. Read it top to bottom; it is the conversation from section 01 written as code: submit, then ask every two seconds with await sleep(2000) until the status is no longer queued or running, then keep the result and switch to the Difference layer. Every setJob redraws the progress bar.

Three choices in there worth noticing. The old result is cleared as soon as Run is pressed, so the map never shows a result that does not match the trees on it. One failed question does not end the run; five in a row do. And nothing is saved in the browser: reloading the page starts clean.

MapArea.jsx · outline, overlay, trees (replace)

Three things on the map. A dashed outline of the scene, drawn from its four corners, so people know where trees can go. The overlay, an image pinned to the same four corners and drawn underneath the outline (beforeId). And one round, draggable marker per tree; double-clicking it removes the tree.

One fix from Week 4 and 5, sorry! initialViewState wants longitude and latitude, not lng and lat; with the wrong names, react-map-gl quietly starts in the ocean at longitude 0, latitude 0.

Panel.jsx · the prototype's panel (replace)

Markup and props, top to bottom like the prototype: the Overlay section (Variable, Layer, opacity, hour, legend, statistics), Trees (add, clear, the list), and Run. Scenario and Difference stay disabled until a run has finished. The progress bar is worked out from phase and timesteps_done: the sky view step is roughly the first 45 %, the 24 hours the rest.

06 Run it on your laptop

The site needs two programs running at the same time, so you need two terminals. In VS Code, open the cool-choices folder and use Terminal → New Terminal twice (or the split button in the terminal panel).

Terminal 1 · the backend

python -m app.baseline only does work the first time (or with --force after the scene changes); afterwards it just says the baseline is already there. The server is ready when it prints Uvicorn running on http://127.0.0.1:8000. Leave it running.

Terminal 2 · the frontend

npm install is needed the first time on each computer, and again whenever package.json changes after a pull. npm run dev starts Vite and prints the address of your site:

(Your version number and time will differ.) Open the Local address in your browser. In VS Code you can hold Cmd (macOS) or Ctrl (Windows) and click it. That is your site. Keep both terminals open while you work; Ctrl+C in a terminal stops that program.

Address What is there
http://localhost:5173 The site. This is the only address you open to use it. Vite forwards anything starting with /api to the backend for you (the proxy from Week 5).
http://localhost:8000/docs The backend's own documentation page, for trying routes by hand. Not the site.
localhost means "this computer"

Nobody else can open your localhost:5173, and you cannot open theirs. Each of you runs your own copy. That is why there is nothing to deploy this week, and why every person's .env with their own Mapbox token is enough.

07 Put it together

Pull everyone's pieces, start both terminals from section 06, open the Local address, and try all of this:

  • The map opens on your scene with its dashed outline and the baseline TMRT at 14:00. Variable switches between TMRT and UTCI, the legend and Baseline mean follow, and ▶ plays through the day.
  • Press Add trees and click inside the outline two or three times, on open ground (streets and plazas show the biggest change). Drag a marker: its coordinates in the list change. Double-click one: it is gone.
  • Press Run analysis. The button says Running…, and the line under the bar goes geometry → simulating · 9/24 h → rendering.
  • When it is done, the Layer is Difference: green around your trees. The statistics now show Scenario mean, Largest cooling and Pixels changed. Switch to Scenario and Baseline and compare; try 10:00 and 14:00.
  • Move a tree and press Run again: the map goes back to the baseline while it runs, then shows the new result.
  • Reload the page: everything is back to the start.

08 When it breaks

The site will not open, or npm run dev printed a different port

Open exactly the Local address it printed. If 5173 is still taken by an old run, Vite picks 5174 and says so; that is fine. If npm run dev fails with vite: command not found, run npm install in frontend/ first.

"Failed to load: Internal Server Error", or the page stays on "Loading scene…"

The backend is not running, or is running on another port. Look at terminal 1: it must say Uvicorn running on http://127.0.0.1:8000. The Vite terminal shows http proxy error ... ECONNREFUSED when it cannot reach it.

"baseline not computed yet", and Run analysis is disabled

Run python -m app.baseline in backend/, then reload the page.

The map opens in the ocean

initialViewState still has lng/lat instead of longitude/latitude. Use the MapArea.jsx from section 05.

"tree(s) fall outside the scene extent"

Every tree must be inside the dashed outline. Remove the one outside (× in the list) and run again.

"unknown job - did the backend restart?"

You saved a backend file during a run, so --reload restarted the server and the run was lost. Press Run again, and leave the backend files alone until it finishes.

"Failed: FileNotFoundError ... scene/Building_DSM.tif"

The backend/scene/ folder is missing or incomplete. It needs exactly Building_DSM.tif, DEM.tif, Trees.tif and ownmet_Forcing_data.txt (section 04).

"Failed:" with a message about memory or admission

The model checked whether the run fits in MEMORY_BUDGET and decided it does not. For a 500 × 500 scene 6 GB is plenty; if your scene is much bigger, cut a smaller one, or raise the number in model.py if your laptop has the memory.

No module named 'solweig_light.runtime_phases'

The old Week 5 version is still installed in this environment. Repeat section 02 with solweig-light active.

ModuleNotFoundError: No module named 'PIL', 'fastapi' or 'solweig_light'

The wrong environment is active, or the requirements are not installed in it: conda activate solweig-light, then pip install -r backend/requirements.txt.

The progress bar does not move

During the geometry step it creeps slowly, for a minute or so; the seconds still count. After that it moves every hour. If the seconds stop, open the browser console (F12), Network tab: there should be a jobs request every two seconds. Also look at the backend terminal: an error from the model appears there.

Done, but the Difference layer looks empty

The difference is real but small: a few trees change a few dozen pixels, and unchanged pixels are white. Zoom in on your trees and try 10:00 or 14:00; at night there is no shade to make. If the Network tab shows a 404 for tmrt_diff_14.png, look at the backend terminal for an error.

The first run takes much longer than the next ones

Normal: the first run after installing compiles the model's kernels and caches them. If every run is slow, close heavy apps; the model uses up to four cores.
